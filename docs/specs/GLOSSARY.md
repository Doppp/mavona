# Mavona terminology

| Term | Meaning |
| --- | --- |
| Surface | A relevant application component, interface or test affected by a task |
| Legibility | How clearly repository structure and conventions can be discovered |
| Task route | Direct change, lightweight plan, full plan or a decision/refusal outcome |
| Rails route | An HTTP endpoint mapping in the target Rails application |
| Evidence | A provenance-bearing observation or executed check result |
| Locality | Where model inference requests may go; distinct from browser/server egress |
| Verifier | A configured or accepted executable check with explicit scope and rationale |
| Independent execution | A harness runner executes the check and records its actual outcome |
| Independent judgment | Acceptance criteria originate outside the implementation agent's self-assessment |
| Protected grader | Benchmark acceptance code structurally hidden from the evaluated agent |
| Worktree lock | Ownership preventing concurrent Mavona mutations in one worktree; not an OS sandbox |
| Widening | Expanding context or verification scope when evidence requires it |
| Baseline | A labelled pre-change observation; never proof of post-change correctness |
| Projection | Rebuildable indexed/UI state derived from canonical events |
| No-boot probe | Parsing in Ruby without loading the target application |
| Runtime probe | Inspection after explicitly loading the Rails environment |
| Engineering preview | Intermediate demonstrable build with openly incomplete product scope |
| v2 | Historical name for the TypeScript design generation; the target product release is v0.1 |
| MVP | The agreed complete usable release, including code viewing and full App Inspection |
| Uplift | Measured improvement in protected task completion relative to a declared baseline |
